# SpriteBatchDemo

엔진 없이 Win32와 Direct3D 11만으로 만든 2D 스프라이트 렌더러입니다.
움직이는 스프라이트 2만 개에 **배칭 · 인스턴싱 · 컬링** 세 가지 최적화를 직접 구현하고,
각각이 렌더 스레드 CPU 부하를 얼마나 줄이는지 **숫자로 실측**합니다.

- **배칭(Batching)** — 드로우 콜을 하나로 묶어 싸게 그린다 → CPU 제출 시간 ↓
- **인스턴싱(Instancing)** — per-instance 데이터로 GPU에 올리는 양을 약 1/3로 ↓
- **컬링(Culling)** — 화면 밖 스프라이트는 아예 그리지 않는다 → 드로우 대상 ↓

`Space`로 Naive/Batched/Instanced 전환, `C`로 컬링 on/off, `WASD`로 카메라 이동.
모든 수치는 창 제목 표시줄에 실시간 표시됩니다.

> 앞서 만든 [MiniD3D11Renderer](https://github.com/AIMHYUK/MiniD3D11Renderer)에서
> 창 생성·디바이스·스왑체인·셰이더·상수 버퍼까지 직접 구현했고, 그 위에
> "드로우 콜을 묶으면 실제로 얼마나 빨라지는가"를 측정 가능한 형태로 만든 것이 이 프로젝트입니다.

## 무엇을 측정하는가

두 모드는 **같은 스프라이트 무리를 똑같은 픽셀**로 그립니다. 다른 것은 정점을 GPU에 올리고
그리는 *방법*입니다. 스프라이트가 움직이므로 위치는 매 프레임 바뀌고, 그 정점을 어떻게 올리느냐가 갈립니다.

| 모드 | 업로드 · 드로우 | 방식 |
|------|-----------------|------|
| **Naive**     | N번 · N번 | 스프라이트마다 정점 4개를 `Map`으로 올리고 → `DrawIndexed(6)`. N번 반복 |
| **Batched**   | **1번 · 1번** | 모든 정점을 한 버퍼에 모아 `Map` 한 번으로 올리고 → `DrawIndexed(N*6)` 한 번 |
| **Instanced** | **1번 · 1번** | 단위 사각형 1개 + per-instance 데이터 N개만 올리고 → `DrawIndexedInstanced`. 업로드가 가장 적다 |

Naive는 실무의 순진한 경로 그대로입니다 — 오브젝트마다 GPU에 데이터를 올리고 그립니다.
`Map(WRITE_DISCARD)`마다 드라이버가 버퍼를 새로 잡고, 드로우 콜마다 CPU→드라이버 왕복이 붙습니다.
이 **per-object 비용**이 스프라이트 수에 비례해 쌓입니다.

Batched는 그 반복을 **한 번의 큰 업로드 + 한 번의 드로우**로 합칩니다. GPU가 하는 실제 렌더링 양은
양쪽이 같으므로, 시간 차이는 **Naive가 매 오브젝트마다 쪼개서 치르는 업로드·드로우 콜 비용**입니다.
이것이 실제 엔진이 배칭/인스턴싱을 하는 이유 그 자체입니다.

## 결과

측정 환경: **AMD Radeon 780M (내장 그래픽)**, 1280×720, **VSync OFF (ALLOW_TEARING)**, Release 빌드, 스프라이트 20,000개

두 단계로 나눠 측정했다.

### ① 정적 배칭 — 위치 고정 (원리 검증)

정점을 한 번 굽고(IMMUTABLE) 매 프레임 그리기만 한다. Batched는 업로드가 아예 없어 극단적인 격차가 난다.

| 모드 | 드로우 콜 | **CPU 제출 시간** | 총 프레임 시간 | FPS |
|------|-----------|------------------|----------------|-----|
| Naive   | 20,000 | 2.883 ms | 3.089 ms | 324 |
| Batched | 1      | **0.001 ms** | 1.937 ms | 516 |

→ CPU 제출 **약 2,900배** 감소. Batched는 업로드가 0이라 사실상 드로우 콜 1번만 남는다.

### ② 동적 배칭 — 매 프레임 이동 (실제 게임 조건, 현재 빌드)

스프라이트가 움직이므로 정점을 매 프레임 다시 올려야 한다. Batched는 정점 N×4개를 **한 번에**,
Instanced는 정점 대신 **인스턴스 N개(약 1/3 데이터)**만 올린다. 세 모드를 Space로 순환한다.

| 모드 | 드로우 콜 | **CPU 제출 시간** | 올리는 데이터 | 총 프레임 | FPS |
|------|-----------|------------------|---------------|-----------|-----|
| Naive     | 20,000 | ~1.8 ms  | 정점 N×4 (N번 쪼개서) | 3.24 ms | 309 |
| Batched   | 1      | ~0.3 ms  | 정점 N×4 (한 번)      | 2.31 ms | 434 |
| Instanced | 1      | ~0.14 ms | 인스턴스 N (한 번)    | 2.16 ms | 463 |

→ Naive→Batched 약 5~8배, **Batched→Instanced 약 2배**(올리는 데이터가 1/3로 줄어), Naive→Instanced 약 13배.
(CPU측 비용이라 실행마다 조금 흔들린다. 견고한 결론은 이 **순서와 자릿수**다.)

### 심화 — "제출 시간"을 Map()과 memcpy로 쪼개 보면

이 CPU 제출 시간이 정확히 무엇인지 확인하려고, Batched 업로드를 `Map()` 호출과 `memcpy`로 나눠 쟀다:

| Batched | `Map()` | `memcpy` | 제출 |
|---------|---------|----------|------|
| 이동 | 0.001 ms | 0.331 ms | 0.334 ms |
| 정지 | 0.001 ms | 0.349 ms | 0.354 ms |

- **`Map()`은 0.001ms — 안 기다린다.** `WRITE_DISCARD`는 VidMM(비디오 메모리 관리자)이 버퍼를
  rename(다른 물리 메모리로 교체)해 GPU 대기를 없앤다. 이 데모는 rename 풀이 넉넉해 stall이 없다.
  ([MS 문서: Requesting to Rename an Allocation](https://learn.microsoft.com/en-gb/windows-hardware/drivers/display/requesting-to-rename-an-allocation))
- 제출 시간의 거의 전부가 **`memcpy`**다. 즉 이 지표는 드라이버/GPU가 아니라 **CPU가 정점을 복사하는 비용**이다.
- 정지가 이동보다 memcpy가 느린 것(0.331→0.349)은 CPU측 효과(캐시가 식고 클럭이 내려감)이며,
  총 프레임 시간이 동일하므로 실제 성능 저하는 아니다.

→ 숫자를 그냥 믿지 않고 **구성 요소로 분해해 원인을 데이터로 확인**한 예.
(이 두 줄은 창 제목 표시줄에 그대로 찍히며, 포트폴리오 페이지에 그 화면을 실어 두었다.)

**두 단계를 함께 보는 이유:** 정적(2,900배)은 배칭의 상한을, 동적(약 5배)은 실제 게임에서 받는
실질 이득을 보여준다. 핵심은 같다 — **&ldquo;작은 업로드·드로우 N번&rdquo;을 &ldquo;큰 업로드·드로우 1번&rdquo;으로
합치면 렌더 스레드 CPU가 그만큼 한가해진다.**

### 두 지표를 나눠 봐야 하는 이유

- **총 프레임 시간(1.4~1.6배)** — GPU가 하는 실제 렌더링 양은 두 모드가 같다. 여기에 바닥이 묶여 크게 안 줄어든다.
- **CPU 제출 시간(정적 2,900배 · 동적 약 5배)** — 배칭이 실제로 없애는 비용. Naive는 매 프레임 CPU가 2만 번 `Map`+드로우를 제출하지만, Batched는 1번뿐이다.

게임 클라이언트에서 병목이 되는 것은 대개 **렌더 스레드 CPU 시간**이다. 그래서 이 프로젝트는
"프레임 빨라졌다"가 아니라 **"렌더 스레드 CPU 제출 부하를 줄였다"** 를 결과로 말한다.

## 컬링 — 안 보이는 건 그리지 않는다

스프라이트를 **화면의 3배 크기 월드**에 뿌리고, 카메라(`WASD`)가 그 일부만 본다.
컬링 ON(`C`)이면 화면 사각형과 안 겹치는 스프라이트를 CPU에서 걸러 **그리기 목록에서 뺀다.**

측정 (카메라 중앙, 화면이 월드의 ~1/9):

| 모드 | 컬링 | 그림 | 드로우 콜 | CPU 제출 | FPS |
|------|------|------|-----------|----------|-----|
| Naive     | OFF | 20,000 | 20,000 | 1.586 ms | 423 |
| Naive     | **ON** | 2,347 | **2,347** | **0.123 ms** | 1410 |
| Instanced | OFF | 20,000 | 1 | 0.046 ms | 1253 |
| Instanced | **ON** | 2,240 | 1 | **0.014 ms** | 1973 |

- Naive+컬링: 드로우 콜 20,000→2,347, CPU 제출 **약 13배** 감소, FPS 3.3배.
- **핵심:** 컬링 ON/OFF는 **화면이 똑같아 보인다**(둘 다 ~2,300개만 화면에 있음). 다른 것은 *처리량*이다 —
  OFF는 화면 밖 1만 7천 개까지 다 처리(GPU가 나중에 잘라냄), ON은 화면에 걸친 것만. **&ldquo;안 보이면 처리하지 않는다.&rdquo;**

배칭이 &ldquo;싸게 그리기&rdquo;, 인스턴싱이 &ldquo;적게 올리기&rdquo;라면, 컬링은 **&ldquo;아예 안 그리기&rdquo;**다. 세 최적화가 겹쳐 쌓인다.

## 조작

| 키 | 동작 |
|----|------|
| `Space` | Naive → Batched → Instanced 순환 |
| `C` | 컬링 on/off (화면 밖 스프라이트 걸러내기) |
| `WASD` | 카메라 이동 (화면보다 큰 월드를 둘러봄) |
| `P` | 움직임 일시정지 (수치 읽기·스크린샷용) |
| `Esc` | 종료 |

모드 / 스프라이트 수 / 드로우 콜 / **CPU 제출 시간** / 프레임 시간(ms) / FPS 는 **창 제목 표시줄**에 실시간 표시됩니다.

## 환경 / 빌드

- Visual Studio 2022 (v143) / C++17 / x64
- Windows SDK (`d3d11.lib`, `dxgi.lib`, `d3dcompiler.lib`, `dxguid.lib`)
- 외부 라이브러리 없음

`SpriteBatchDemo.sln`을 VS2022로 열고 x64 / **Release** 로 빌드 후 실행합니다.
(성능 비교는 최적화가 켜진 Release 에서 해야 의미가 있습니다.)
산출물은 `build\x64\Release\` 에 생기고, 셰이더는 빌드 후 exe 옆으로 자동 복사됩니다.

> **툴셋 관련:** 이 프로젝트는 최신 MSVC 툴셋(v145)으로 설정돼 있습니다.
> "빌드 도구를 찾을 수 없습니다" 경고가 뜨면, 솔루션 우클릭 → **[솔루션 대상 변경(Retarget)]**
> 에서 설치된 툴셋(예: v143)을 고르면 그대로 빌드됩니다. 소스 코드는 동일합니다.

## 구조

```
src/
  main.cpp       진입점. 창과 렌더러를 연결하고 게임 루프를 돌린다.
  Window.*       Win32 창 하나. D3D를 모른다. 크기 변경·키 입력은 콜백으로만 알린다.
  Renderer.*     디바이스·스왑체인·스프라이트 버퍼를 소유하고,
                 Naive/Batched/Instanced 세 경로로 한 프레임을 그린다.
  FrameTimer.h   QueryPerformanceCounter 기반 평균 FPS / 프레임 시간(ms) 측정.
  Common.*       COM 스마트 포인터 별칭, HRESULT 검사 매크로, exe 기준 경로 해석.
shaders/
  Sprite.vs.hlsl          Naive·Batched 공용. 픽셀 좌표 -> NDC 변환, UV 전달.
  SpriteInstanced.vs.hlsl 인스턴싱 전용. 단위 코너 × 인스턴스 크기 + 인스턴스 위치.
  Sprite.ps.hlsl          세 모드 공용. 아틀라스 샘플 × 정점 색. 알파 블렌딩.
```

## 텍스처 아틀라스

도형 4종(원·링·다이아몬드·+)을 **한 장(256×256)에 코드로 그려** 담고, 스프라이트마다
그중 하나를 UV로 뽑아 씁니다. 외부 이미지 파일도, 로딩 라이브러리도 없습니다(무의존성).

한 장에 모아둔 덕에 **텍스처 바인딩을 스프라이트마다 바꿀 필요가 없습니다** — SRV 한 번 꽂으면
20,000개를 배칭 드로우 한 번으로 다 그립니다. 실제 엔진에서 아틀라스를 쓰는 이유(텍스처
전환=state change 제거)를 그대로 보여줍니다. 알파 블렌딩으로 도형 가장자리를 배경과 섞어
네모가 아니라 빛나는 파티클처럼 보이게 했습니다.
