# MiniD3D11Renderer → SpriteBatchDemo: 무엇이 어떻게 달라졌나

이 프로젝트는 [MiniD3D11Renderer](https://github.com/AIMHYUK/MiniD3D11Renderer)에서
바로 이어집니다. 그쪽은 "창 띄우고 D3D11로 **스프라이트 하나** 그리기"까지였고,
여기서는 그 구조를 그대로 물려받아 **수만 개를 두 방식으로 그려 성능을 실측**하는
렌더러로 확장했습니다.

이 문서는 두 프로젝트가 파일·기법·설계 의도 면에서 **정확히 무엇이 다른지**를 정리합니다.

---

## 0. 한눈에 보는 대조표

| 항목 | MiniD3D11Renderer | SpriteBatchDemo | 왜 바꿨나 |
|---|---|---|---|
| 목표 | 스프라이트 **1개** 화면에 | 스프라이트 **20,000개**를 Naive/Batched로 | 배칭의 효과를 측정하려면 다수·두 경로가 필요 |
| 정점 좌표 | 단위 사각형(0~1) 1개 + 상수버퍼로 위치 | **픽셀 좌표를 정점에 직접 구움**(N×4개) | 스프라이트마다 위치가 달라 CB로는 배칭 불가 |
| 드로우 | `DrawIndexed(6)` 1번 | Naive N번 / Batched 1번 | 두 방식의 비용 차이가 이 프로젝트의 주제 |
| 인덱스 타입 | `uint16` (R16_UINT) | `uint32` (R32_UINT) | N×4 정점이 65,535를 넘음 |
| VSync | `Present(1, 0)` — 켬 | `Present(0, ALLOW_TEARING)` — 끔 | 목적이 정반대. 성능차를 보려면 상한을 풀어야 |
| 계측 | 평균 FPS | **CPU 제출 시간(ms)** + 프레임 시간 + FPS | 배칭이 이기는 곳은 렌더 스레드 CPU |
| 텍스처 | 없음(정점 색만) | **코드 생성 아틀라스** + UV + 샘플러 | 게임처럼 보이게 + 텍스처 바인딩 절약 스토리 |
| 블렌딩 | 없음(불투명) | **알파 블렌딩** | 도형 가장자리를 배경과 부드럽게 |
| 움직임 | 정지 | **매 프레임 이동**(경계 튕김) | 실제 게임 조건 = 동적 배칭(매 프레임 재업로드) |
| 카메라·컬링 | 없음 | **카메라 + 큰 월드 + 컬링** | 화면 밖 스프라이트는 안 그린다(안 보이면 처리 X) |
| 파일 | Common/Window/Renderer/FrameTimer/main | 동일 구조 + 확장 | 익숙한 뼈대를 그대로 계승 |

아래에서 하나씩 자세히 봅니다.

## 1. 정점을 다루는 방식 — 단위 사각형+상수버퍼 → 픽셀 좌표 베이킹

**MiniD3D11Renderer:** 정점 버퍼에 "단위 사각형"(좌상단 0,0 ~ 우하단 1,1) **하나**만
IMMUTABLE로 두고, 실제 화면 위치·크기는 상수 버퍼(`SpriteConstants`)로 넘겼습니다.
정점 셰이더가 `비율 → 픽셀 → NDC`로 변환했죠. 스프라이트 하나엔 이게 가장 깔끔합니다.

**문제:** 이 방식으로는 여러 개를 한 번에 못 그립니다. 스프라이트마다 위치가 다른데
그 위치가 상수 버퍼에 들어 있으니, 개수만큼 상수 버퍼를 바꿔가며 그려야 합니다.
= 개수만큼 드로우 콜. **배칭이 원천적으로 불가능한 구조**입니다.

**SpriteBatchDemo:** 그래서 각 스프라이트의 **네 꼭짓점을 픽셀 좌표로 CPU에서 미리 구워**
정점 버퍼에 넣습니다. 이제 모든 스프라이트가 같은 좌표계(픽셀)에 있으므로, 한 버퍼에
전부 모아 한 번의 드로우로 그릴 수 있습니다. 정점 셰이더는 `픽셀 → NDC`만 합니다.

```
MiniD3D11Renderer:  단위 사각형 1개  +  상수버퍼(위치)  →  스프라이트 1개
SpriteBatchDemo:    픽셀 좌표 N×4개(버퍼에 구움)        →  스프라이트 N개(배칭 가능)
```

> 정점 구조체도 바뀌었습니다. `{x, y, r,g,b,a}` → `{x, y, u,v, r,g,b,a}` (UV 추가, 8장 참고).

## 2. 그리는 경로가 둘이 됐다 — Naive vs Batched

이 프로젝트의 핵심은 **같은 장면을 두 가지 방법으로 그려 비교**하는 것입니다.

### Naive — MiniD3D11Renderer 방식을 N번 반복

MiniD3D11Renderer가 한 프레임에 하던 일(정점/상수를 GPU에 올리고 → `DrawIndexed`)을
**스프라이트마다** 반복합니다. 구체적으로는 정점 4개를 작은 **동적 정점 버퍼**에
`Map(WRITE_DISCARD)`로 올리고 → 그린다, 를 N번. 이게 실무의 순진한 per-object 경로입니다.

### Batched — 전부 한 번에

모든 스프라이트 정점이 이미 한 IMMUTABLE 버퍼에 구워져 있으므로, 업로드 없이
`DrawIndexed(N*6)` **한 번**으로 끝냅니다.

### 설계 과정에서 겪은 것 (기록용)

처음엔 Naive를 "가장 싸게" 만들었습니다 — 큰 버퍼를 한 번 바인딩하고 오프셋만 바꿔
`DrawIndexed(6, i*6, 0)`를 N번. 그런데 측정해보니 격차가 **1.35배**뿐이었습니다.
이유: 이 Naive는 드로우 콜당 비용이 ~16ns라, GPU가 실제로 그리는 비용(양쪽 공통)에
묻혔습니다. 그래서 **실무의 진짜 Naive(per-object Map+draw)**로 바꿨고, 그제서야
의미 있는 차이가 났습니다. → 자세한 수치는 5장·10장.

## 3. 계측 — 평균 FPS 하나 → CPU 제출 시간 + 프레임 시간

**MiniD3D11Renderer:** `FrameTimer`가 평균 FPS만 냈습니다(제목 표시줄).

**SpriteBatchDemo:** 두 가지를 더합니다.

1. **프레임 시간(ms)** — FPS는 큰 수라 차이가 눈에 안 들어옵니다(516 vs 324).
   프레임 시간은 작은 수라 선명합니다(1.94 vs 3.09ms). 게다가 더하고 나눌 수 있어 정직합니다.
2. **CPU 제출 시간(ms)** — 드로우를 "제출"하는 데 든 렌더 스레드 CPU 시간을 `QueryPerformanceCounter`로
   직접 잽니다. **이게 이 프로젝트에서 가장 중요한 지표입니다.**

왜 CPU 제출 시간이 핵심인가: 총 프레임 시간은 GPU가 하는 실제 렌더링(양쪽 동일)에
바닥이 묶여 1.6배밖에 안 줄어듭니다. 하지만 **CPU가 드로우를 던지는 비용은
Naive(2만 번)와 Batched(1번)가 약 2,900배 차이**입니다. 게임 클라이언트에서
병목이 되는 것은 대개 이 렌더 스레드 CPU 시간이므로, 이 지표라야 배칭의 진짜 이득이 보입니다.

---

## 4. VSync — `Present(1, 0)` → `Present(0, ALLOW_TEARING)`

목적이 **정반대**라 여기서 갈립니다.

**MiniD3D11Renderer:** 화면 찢김 없이 보는 게 목적이라 `Present(1, 0)`(VSync 켬)이었습니다.

**SpriteBatchDemo:** 성능을 재려면 프레임 상한을 풀어야 합니다. VSync가 켜져 있으면
프레임 시간이 모니터 주사율(60Hz→16.6ms)에 고정돼 두 모드가 똑같아 보입니다.

여기서 함정을 하나 겪었습니다. `Present(0, 0)`으로 SyncInterval을 0으로 줬는데도
두 모드가 똑같이 **16.677ms(정확히 60FPS)**로 나왔습니다. 원인은 **플립 모델 스왑체인 +
창모드**의 특성 — SyncInterval 0으로도 DWM(윈도우 합성기)이 주사율로 다시 묶습니다.

진짜로 풀려면 **tearing(테어링)**을 켜야 합니다(세 곳이 맞아야 함):
1. `IDXGIFactory5::CheckFeatureSupport(DXGI_FEATURE_PRESENT_ALLOW_TEARING)`로 지원 확인
2. 스왑체인 생성/`ResizeBuffers`에 `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING`
3. `Present(0, DXGI_PRESENT_ALLOW_TEARING)`

이걸 넣고서야 프레임 시간이 갈라졌습니다.

---

## 5. 인덱스 타입 — `uint16` → `uint32`

**MiniD3D11Renderer:** 스프라이트 1개 = 정점 4개라 인덱스가 `uint16`(R16_UINT)로 충분했습니다.

**SpriteBatchDemo:** 스프라이트 20,000개 = 정점 80,000개. `uint16`의 한계(65,535)를 넘으므로
`uint32`(R32_UINT)로 올렸습니다. 작지만 안 바꾸면 65,535번째 정점부터 인덱스가 엉킵니다.

---

## 6. 텍스처 — 없음 → 코드 생성 아틀라스 + UV + 샘플러 + 알파 블렌딩

**MiniD3D11Renderer:** 텍스처 없이 정점 색만 보간해 그렸습니다(그라데이션 사각형).

**SpriteBatchDemo:** 파이프라인에 텍스처 단계를 통째로 추가했습니다.

- **아틀라스를 코드로 생성** — 도형 4종(원·링·다이아몬드·+)을 256×256 한 장에 그립니다.
  외부 이미지·라이브러리 없이(무의존성) `GenerateAtlasPixels()`가 알파로 도형을 새깁니다.
- **UV** — 정점에 UV를 추가하고, 스프라이트마다 아틀라스 4칸 중 하나를 골라 그 칸의 UV를 굽습니다.
- **SRV + 샘플러** — 텍스처를 셰이더가 읽는 뷰(SRV)로 만들고, 선형 필터 + 클램프 샘플러를 붙입니다.
- **알파 블렌딩** — `SrcAlpha / InvSrcAlpha`로 도형 가장자리를 배경과 섞어, 네모가 아니라
  빛나는 파티클처럼 보이게 합니다.

**배칭과의 연결:** 여러 종류를 **한 장에 모아둔** 덕에 텍스처 바인딩을 스프라이트마다 바꿀
필요가 없습니다. SRV 한 번 꽂으면 20,000개를 배칭 드로우 한 번으로 다 그립니다.
이것이 실제 엔진에서 아틀라스를 쓰는 이유(텍스처 전환 = state change 제거)입니다.

## 7. 파일 구조 대조

뼈대는 그대로 물려받았습니다. 무엇이 같고 무엇이 바뀌었는지:

| 파일 | 상태 | 내용 |
|---|---|---|
| `Common.h/.cpp` | **거의 동일** | `ComPtr`, `HR_CHECK`, `ResolvePathFromExe` — 그대로 재사용 |
| `Window.h/.cpp` | **확장** | 리사이즈 콜백에 더해 **키 입력 콜백**(Space 토글) 추가 |
| `FrameTimer.h` | **확장** | 평균 FPS에 **평균 프레임 시간(ms)** 추가 |
| `Renderer.h/.cpp` | **대폭 확장** | 배칭/Naive 두 경로, 아틀라스, tearing, CPU 제출 계측 |
| `Sprite.vs.hlsl` | **변경** | 픽셀→NDC + **UV 전달** |
| `Sprite.ps.hlsl` | **변경** | 정점 색 → **아틀라스 샘플 × 정점 색** |
| `main.cpp` | **확장** | Space 토글 연결, 제목에 CPU 제출/프레임/FPS |
| `.sln/.vcxproj` | 동일 방식 | v143(→로컬 v145) / C++17 / x64, 셰이더 복사 |

## 8. 측정 결과 요약

측정: AMD Radeon 780M(내장 그래픽), 1280×720, VSync OFF(ALLOW_TEARING), Release, 스프라이트 20,000개.
정적(위치 고정) → 동적(매 프레임 이동)으로 두 단계 측정했다.

**① 정적 배칭** (정점을 한 번 굽고 그리기만)

| 모드 | 드로우 콜 | CPU 제출 시간 | 총 프레임 시간 | FPS |
|---|---|---|---|---|
| Naive   | 20,000 | 2.883 ms | 3.089 ms | 324 |
| Batched | 1      | **0.001 ms** | 1.937 ms | 516 |

→ CPU 제출 **약 2,900배**. Batched는 업로드가 0이라 드로우 콜 1번만 남는 극단적 격차.

**② 동적 배칭** (스프라이트가 움직여 매 프레임 정점 재업로드 — 현재 빌드, 3모드)

| 모드 | 드로우 콜 | CPU 제출 시간 | 올리는 데이터 | FPS |
|---|---|---|---|---|
| Naive     | 20,000 | ~1.8 ms  | 정점 N×4 (N번 쪼개) | 309 |
| Batched   | 1      | ~0.3 ms  | 정점 N×4 (한 번)    | 434 |
| Instanced | 1      | **~0.14 ms** | 인스턴스 N (한 번) | 463 |

→ Naive→Batched 약 5~8배, Batched→Instanced 약 2배(데이터 1/3), Naive→Instanced 약 13배.

- 정적(2,900배)은 배칭의 상한, 동적(약 5배 이상)은 실제 게임에서의 실질 이득.
- 총 프레임 시간은 GPU 바닥에 묶여 1.4~1.6배 (양쪽 렌더링 양이 같으므로)
- **심화**: 제출 시간을 Map()/memcpy로 쪼개보니 **Map()은 0.001ms(안 기다림)** — WRITE_DISCARD가
  VidMM rename으로 GPU 대기를 없앰. 제출 시간의 거의 전부가 memcpy(CPU측)였다. 즉 이 지표는 드라이버가
  아니라 CPU 복사 비용. 추측이 아니라 쪼개서 측정해 확인.

## 9. 정리 — 이 프로젝트가 보여주는 것

MiniD3D11Renderer가 "D3D11로 그림 하나 띄우기"를 익히는 과정이었다면,
SpriteBatchDemo는 그 위에서 **"구조 선택을 측정으로 정당화하기"**를 보여줍니다.

- 단일 스프라이트 구조는 왜 배칭이 안 되는지 → 픽셀 좌표 베이킹으로 해결
- "VSync 껐는데 왜 60FPS?" → 플립 모델 + tearing의 함정을 규명
- "배칭이 빠르다"를 정적(2,900배)·동적(약 5배)으로 나눠 재고, 총 프레임(GPU 바닥) vs CPU 제출로 **어디서** 빨라지는지 구분
- 정적(고정)에서 원리를 검증하고 동적(움직임)으로 확장해 **실제 게임 조건**까지
- 아틀라스로 텍스처 전환을 없애 배칭을 뒷받침
- **배칭(싸게 그리기) · 인스턴싱(적게 올리기) · 컬링(아예 안 그리기)** 세 최적화를 한 프로젝트에 쌓음

다음 단계(움직이는 스프라이트의 DYNAMIC 배칭, 인스턴싱, 컬링)는 `README.md` 참고.
